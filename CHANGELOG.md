# Changelog

All notable changes to this project are documented here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and the project uses [Semantic Versioning](https://semver.org/).

The repository has two version numbers: the app (front end, edge functions and database), in the root `package.json`,
and the QR service, in `qr-service/package.json`. Each entry is named after the app version and states both.

## [Unreleased]

Nothing yet. At a release the title of this section becomes `[X.Y.Z] - <date>`, together with the version in `package.json` (the
`./echo upgrade` command prints the section whose title carries the version it just installed).

## [2.13.0] - 2026-11-26

App `2.13.0` (`package.json`) and QR service `2.5.17` (`qr-service/package.json`).

First public release. Both version numbers continue the internal history of the project; earlier versions were not published.

Installation with Docker: `git clone` and `./install.sh` bring up the whole of Echo on one machine, with no Supabase account, CLI or hosted
project, and no Vercel.

### App

- **Docker installation.** `docker-compose.yml` with ten services (Postgres 17, GoTrue, PostgREST, Realtime, Storage, a Deno process that runs the 46 edge
  functions, the QR service, and a Caddy gateway that serves the front end and every API under one origin), `install.sh` (installer) and `echo`
  (`status`, `logs`, `up`, `down`, `restart`, `upgrade`, `backup`, `restore`, `reset-password`, `recovery-link`, `setup-link`, `doctor`, `psql`, `env check`).
  Four modes: localhost (default), own domain with automatic HTTPS, behind a reverse proxy (on the host or in a container), by IP address.
  The four Echo images are built on the machine; nothing is published. Requires Docker Compose 2.24.7 or newer.
- **`.env` generated by the installer** (`docker/tools/gen-keys.mjs`) with new secrets, a guard that makes the database refuse example, empty or malformed
  secrets, and the Vault, the AI-key secret and the Web Push (VAPID) keys created for you. `.env.example` is now the model of that `.env`; the front-end
  variables for development moved to `.env.development.example` (copy it to `.env.development.local`).
- **First access screen** (`/setup`, edge function `primeiro-acesso`, migration `20260102000000_primeiro_acesso.sql`): the first administrator and organization are
  created with the code printed by the installer (`ECHO_SETUP_TOKEN`); it closes by itself afterwards. `/` now redirects (setup, dashboard or login); the landing
  page was removed from the app.
- **Runtime configuration of the front end** (`/config.js`, `src/lib/runtimeConfig.ts`): one build serves any installation. Precedence per field: `/config.js`,
  then `VITE_*`, then the origin of the page. `npm run build` no longer needs any `VITE_*`.
- **Internal × public URL rule.** `ECHO_PUBLIC_URL` is the one public address; servers talk to each other through `http://gateway:8000`. URLs that leave the
  server (saved media, links, webhooks, the Instagram login) use the public one. Without `ECHO_PUBLIC_URL` nothing changes (Supabase Cloud setup).
- **E-mail is optional**: generic SMTP (`SMTP_*`, `nodemailer`), Resend, or none. No edge function answers 5xx for lack of e-mail configuration; invitations
  return a link to copy, the login screen tells the user to ask the administrator for a password link when there is no SMTP, and `./echo reset-password` and
  `./echo recovery-link` do it from the server. A "Change password" card was added to the profile settings, and the minimum password length is 8
  everywhere (sign-up by invitation, recovery, setup).
- **SSRF guard on every URL a tenant or user chooses** (organization webhooks, automation webhook and survey nodes, link previews, media URLs of the API, template
  header samples): `fetchExterno` and `fetchMidia` in `_shared/url-guard.ts`, with a check at every redirect hop. `ECHO_OUTBOUND_ALLOW_HOSTS` allows exact hosts of
  a private network. This also applies to the Supabase Cloud setup.
- `get_decrypted_ai_key` is executable by the service role only (the three edge functions that read AI keys already used it); an organization admin can no longer
  read the key back through the API.
- `send-invitation` no longer scans the Auth user list to recover an account that exists without a profile row: such an orphan account is not repaired by a new
  invitation any more (the previous scan did not scale). It also escapes HTML in the e-mail, and its response gained `email: "enviado" | "nao_configurado" | "falhou"`.
- Edge functions: new scripts `test:router`, `check:verify-jwt`, `test:infra`, `smoke:selfhost` and `test:sql`; `check:edge` covers all 46 functions, the runtime and
  `echo-admin`. A scanner (`tests/processo-unico/`, part of `test:edge`) enforces the rules of the single-process runtime.
- A Content-Security-Policy violation that the audio recording library (`opus-recorder`) caused on every load of the dashboard was fixed at build time.
- Documentation rewritten around the installation: `docs/self-hosting.md`, `reverse-proxy.md`, `backup.md`, `upgrading.md`, `email.md`, `troubleshooting.md`, `development.md`,
  an updated `architecture.md`, and the previous guide moved to `docs/alternatives/supabase-cloud.md`. Issue and pull request templates, `CODE_OF_CONDUCT.md`,
  `SUPPORT.md` and a CI job (`selfhost`) that runs the smoke test.

### Notes for Supabase Cloud or CLI installations

- The Docker installation is the recommended path. On a Supabase Cloud or CLI project, apply the migrations (`npx supabase db push`), deploy the
  functions and set the edge secrets; `ECHO_SETUP_TOKEN`, `SMTP_*` and `ECHO_OUTBOUND_ALLOW_HOSTS` are optional. A webhook of an organization
  that points at a private-network address is refused until you list the host in `ECHO_OUTBOUND_ALLOW_HOSTS`. The guide is
  `docs/alternatives/supabase-cloud.md`.
- **A Supabase Cloud installation does not migrate to the Docker one**, and the address of a Docker installation cannot be changed after the install.

### QR service (`qr-service/`)

- **The image runs as the non-root user `node` (uid 1000), and it has a `HEALTHCHECK`.** Base image `node:22.22.3-alpine3.24`. **Existing volumes:** a volume
  of sessions created by an image that ran as root is owned by root, and this image refuses to boot with
  `[FATAL] o diretório de sessões (/app/sessions) não aceita escrita`. Give the volume to the new user once, before starting it:

  ```bash
  docker run --rm -u 0 -v <volume>:/app/sessions --entrypoint chown <image> -R 1000:1000 /app/sessions
  ```

  For the standalone `qr-service/docker-compose.yml` the volume is `qr_sessions` (prefixed with the Compose project name) and `<image>` is the service image. A
  new installation, and a volume that was empty, need nothing.
- `ECHO_PUBLIC_URL` (optional): the public address used to build the URLs of media and profile pictures saved in the database, for when `SUPABASE_URL` is an
  internal address. A value that is not an `http(s)` URL makes the service refuse to boot. Without it nothing changes.
- A `media_url` that points at the installation's own Storage is downloaded through `SUPABASE_URL`, without the SSRF guard and without following redirects;
  any other URL still goes through the guard.
- The resumable upload rewrites a `Location` from another origin to the origin of its endpoint.
- The QR code stream (Server-Sent Events) writes its headers and a first comment at once and a `: ping` every 25 seconds, so a reverse proxy streams it.
- The service refuses to boot when the sessions directory is not writable, instead of reporting healthy.

### App: database, security and configuration

- Database delivered as a single baseline (`supabase/migrations/`) that applies from scratch with `supabase start`,
  plus migrations for Auth and Storage, reference data and cron jobs.
- URLs and keys used by SQL functions and cron jobs are read from the Supabase Vault (`project_url`,
  `service_role_key`, `qr_service_url`, `ai_key_secret`), with no built-in defaults.
- `scripts/bootstrap-admin.mjs` (`npm run bootstrap:admin`) creates the first administrator and organization.
- The Auth hook `before_user_created` (invite-only sign-up) ships in the baseline but is off by default in
  `supabase/config.toml`; turn it on after creating the first administrator.
- `QR_WEBHOOK_SECRET` is required: without it the `/qr-*` routes of `whatsapp-webhook` answer 503 (the QR service
  also refuses to start without it).
- Server-to-server edge functions reject callers without a service credential by default
  (`EDGE_INTERNAL_AUTH_ENFORCE=0` is a migration escape only).
- The secret columns of `organizations` are not readable through table queries; the settings screens use the RPCs
  `get_org_whatsapp_config` and `get_org_ai_config`.
- E-mails need `EMAIL_FROM` and `SITE_URL` (no built-in defaults). The full list of edge secrets is in
  `supabase/functions/.env.example`.
- Self-hosting guide, architecture notes and contribution guide in `docs/` and at the repository root.

### QR service: what it is and how it is configured

- HTTP service (Express) that connects WhatsApp numbers by QR code or pairing code and serves Echo: `/session`,
  `/message`, `/groups`, `/profile`, `/sticker` and `/call` routes, authenticated by the Supabase `service_role` key
  or a Supabase user token, with a per-number organization check.
- Two WhatsApp providers behind the `WhatsAppClient` adapter: `baileys` (default, file-based sessions) and `zapo`
  (PostgreSQL store, enabled by `ZAPO_PG_URL`), with migration of a number between providers without a new QR scan.
- Delivery of inbound events to Echo's `whatsapp-webhook` (`/qr-*` routes, `x-qr-secret` header) through an outbox
  with in-memory retries, disk spill and replay at boot.
- Inbound media up to `MAX_MEDIA_BYTES`, streamed to disk and uploaded with resumable (TUS) uploads above
  `MEDIA_STREAM_THRESHOLD_BYTES`.
- Voice calls on the `zapo` provider with the `Dockerfile.voip` image.
- Ban-risk protections configurable by environment variables: pairing cap, cooldown after fatal disconnects,
  new-contact cap, reach-out lock on error 463, optional send spacing, staggered restore.
- `Dockerfile`, `Dockerfile.voip`, `docker-compose.yml` (service plus a PostgreSQL for zapo) and a commented
  `.env.example`, all inside `qr-service/`, which is an npm project of its own (the root is not a workspace).

Configuration to know:

- The service lives in the `qr-service/` folder of this repository. Its build and tests run as the `qr-service` job
  of the single CI workflow (`.github/workflows/ci.yml`).
- `docker-compose.yml` requires `ZAPO_PG_PASSWORD` (no default) for the zapo Postgres; generate it with
  `openssl rand -hex 24` before the first `docker compose up`.
- The disconnect alert to Echo's `send-disconnect-alert` edge function authenticates with `SUPABASE_SERVICE_KEY`
  (plus the `apikey` header).
- `ALLOWED_ORIGINS` defaults to `http://localhost:8080,http://localhost:5173` only.
- `/session/health` reports `service: "echo-qr-service"`.
- `QR_WEBHOOK_SECRET` is required: the service refuses to boot without it, and `docker-compose.yml` refuses to run
  without it. Echo's `whatsapp-webhook` answers 503 on the `/qr-*` routes when it has no secret, so both sides must
  have the same value.
- `SUPABASE_SERVICE_KEY` must be the legacy `service_role` JWT, the same value Echo's edge functions send as Bearer
  token (compared byte for byte).
- `docker-compose.yml` maps `host.docker.internal` to the host, so a local Supabase on the same machine is reachable
  from the container on Linux too.
